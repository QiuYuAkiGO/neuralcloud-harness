# Chat Worker 会话历史自压缩实施方案

2026-11-24。调研时的代码基线为 Harness `e3fbe4d`，内网运行版本为 `d2c28ad`。实施分支从 `cf0513c` 开始，随后合入 `de8383f` 的共享身份目录与原用途复核。首版缺省关闭，实施和实测结果见第八节。

建议由 **Chat Worker 用自身模型整理同一会话较早的对话，Java 宿主管理输入范围、来源权限和摘要版本**。下一轮优先保留最近对话的原文，在前面放一段可追溯的历史提要。这样，用户隔了许多轮再说“继续上次那件事”时，Worker 仍有线索理解指代。用户要核对原话、最新约定或行动结果时，继续走现有的受众查证或回执路径。

## 一、已有要求和实现依据

- **短期上下文按会话隔离。** 架构提案要求不同会话分别持有工作上下文，主体身份和长期经历由既有系统维护。Java 首期将记忆读取交给有需要的 Worker，写入由 Router 提交。Master 维护的角色偏好对 Chat Worker 只读。会话提要因此存放在 Harness 本地，供原会话续聊使用。[认知架构](master-worker-cognitive-architecture-20261117.md) · [Java 职责分工](master-worker-router-java-implementation-20261118.md) · [Chat Worker 的只读偏好](master-worker-runtime-discussion-20261117.md#42-chat-worker)
- **区分当事人发言、角色表达与行动结果。** 网页写出响应、QQ 收到 OneBot 成功回执后，才能确认 Misty 的话已送出。涉及事实与原话的查询保留来源、可见范围和更正关系。下一轮开始时，先按当前受众重读已变更的依据，来源也可能在版本号未变时失效。[正式会话入口](console-free-chat-pipeline-20261121.md) · [更正时机和来源状态](master-worker-design-revisions-20261121.md)
- **当前 Java 回放的是原文。** `AuditLog.dialogueBefore` 在当前请求之前选择同渠道同链的用户消息，以及可沿因果链追到已送达回复的记录。它跳过带 `source_refs` 的交付，遇到 `memory_context_reset` 清空旧前缀，最后从新到旧保留整条消息，历史上限为 48,000 个 UTF-16 代码单元。投影到 `DialogueMessage` 后仅余发言角色和正文。压缩必须在这一步裁剪**之前**取得带来源的旧前缀。[原文回放实现](../../java/src/main/java/neuralcloud/controlplane/console/AuditLog.java#L169-L218) · [当前消息类型](../../java/src/main/java/neuralcloud/controlplane/worker/DialogueMessage.java)
- **有两项可借鉴的实现。** 旧 MistyAI 的会话交接用前一份提要和新增事件整理主题、明确约束、尚待处理的请求，并记录来源序号与摘要哈希。其提示词明确区分草稿、发送尝试和送达，正常沉默也不会变成补发待办。当前 Java Master Epoch 提供了冻结边界、保留增量和原子提交的参考。Chat Worker 可以借用这些约束，继续使用自己的会话 ID 和模型。递归摘要论文也采用“先前提要＋新对话”的更新方式，其公开实验只作方法依据。[MistyAI 提要](https://github.com/QiuYuAkiGO/MistyAI/blob/0f8ec938761389fbcece2432741124ebe0ac4aad/compatibility/harness/resident/continuity.mjs) · [MistyAI 交接](https://github.com/QiuYuAkiGO/MistyAI/blob/0f8ec938761389fbcece2432741124ebe0ac4aad/compatibility/harness/resident/runtime.mjs) · [Java Epoch 契约](master-worker-runtime-discussion-20261117.md#103-java-首版换代契约2026-11-23) · [Wang 等的研究](https://arxiv.org/abs/2308.15022)

**用于定水位的数据有限。** 11 月 24 日 09:34（北京时间）导出的既有 QQ 回放审计中，有 1,277 条 `qq_message` 和 5 条 `chat_worker_turn_plan`。这份导出没有入站正文，5 条规划记录也只含 `kind`。它能核对入口数量，无法据此估算长会话比例、token 节省或额外延迟。第六节用完整受控回放测量这些指标。[回放快照口径](../harness/dialogue-playground.md#选择历史截点)

## 二、哪些入口采用提要

1. 网页 `chat-worker`、已启用的 `conversation` 对话编排与 QQ 私聊、允许回复的群聊，在进入轮次规划前共用一份会话投影。启用 Memory 的路径先执行 `MemoryCall.startTurn()`。无 Memory 的网页路径从同一投影读取本地可见原文，依赖 Memory 核验的材料只有在查询成功后才可使用。
2. QQ 普通群消息先按现有近期原文和只读偏好做 `AMBIENT` 参与判断。决定参与并进入轮次规划后才允许触发压缩。仅观察群、`SKIP`、只向角色转达已批准正文的派单和只作通知查证的手机入口，按各自当前契约处理。首版不为这些入口新增会话历史。
3. 提要进入规划及本轮原本就读取对话历史的回复或查证调用。一次规划取得的快照在同一轮复用。Router 的原文分流、任务执行参数、Memory 证据、Master 意图及渠道送达判定继续来自各自的正式入口。提要中的“我去核实”只能帮助理解后续指代，实际执行状态须查对应回执。[入口装配与 QQ 参与判断](../../java/src/main/java/neuralcloud/controlplane/app/ConsoleMain.java#L410-L449) · [轮次开始与回复分派](../../java/src/main/java/neuralcloud/controlplane/app/ConsoleMain.java#L586-L614)

## 三、何时压缩、怎样组装下一轮

**启用和预算。** 在 Chat Worker 的模型配置中新增 `contextCompression=OFF|ROLLING`，缺省为 `OFF`，兼容已有配置。`ROLLING` 可指定 `historyBudgetUnits=B`，拟定有效范围为 4,096 至 48,000，缺省 48,000。无效枚举、非整数、越界值或在 `OFF` 下单配预算，均在配置读取边界报出对应字段。每个模型档位独立设置。以下数字使用 Java `String.length()` 的单位，正文和提要的可见标签一并计入历史预算。

- **触发**。有效旧提要与其后尚未覆盖的合格原文长度之和达到 `floor(3B/4)` 时尝试一次压缩。默认触发点 **36,000**。
- **整理目标**。压缩后历史目标为 `floor(B/2)`，其中提要最多 `floor(B/12)`，余量优先保留完整的最近原文。默认分别是 **24,000、4,000、20,000**。从末尾选择能放进近期额度的最长连续整消息，其前方最早的一段才是本次候选输入。长度按实际渲染计算，最终整段历史硬上限为 **48,000**。
- **模型窗口**。本轮用户原文、系统约束、工具定义、图片及本轮查询材料另占模型窗口。为每个启用档位按最长请求实测完整输入与输出预留，必要时调低 `B`。供应商用量中的输入 token 和缓存命中量分别记录。不得把 UTF-16 数或缓存未命中数换算成模型已用窗口。

**每个参与轮次最多增加一次摘要调用。** 首版在轮次规划前同步尝试，便于确定本轮究竟使用哪个版本，并量出额外延迟。低于触发点且没有待续分片或积压时，直接使用已提交提要和原文尾部。达到触发点先检查是否有可整理的旧前缀。若仅最新一条就超过近期额度，但与有效提要合计仍能放入硬上限，保留这条完整发言，允许暂时超过整理目标。无旧前缀可压时不调用模型。其余情况下按请求截点冻结输入，再释放审计锁调用模型。压缩调用也受该档位预算和现有请求超时约束，输入包括上版提要及一段连续的新历史。跨多批的旧会话按原顺序在后续参与轮次继续。

单条历史消息超过单次压缩输入预算时，仅对压缩输入按 Unicode 码点边界分片，以“原事件＋UTF-16 起止偏移”记录进度，下一批从已提交的偏移继续。面向对话的近期原文仍按整条发言装入。本轮用户输入原样保留。仅由当前输入和固定材料造成的模型超窗，沿该模型调用的错误契约返回。

**同一轮输入顺序。** 稳定角色规则 → 标明“同会话历史提要”的数据块 → 最近的原始用户与 Misty 发言 → 本轮用户问题及当前 Memory 材料。两种协议共用同一份语义投影。Gemini 将提要编码为独立的 `user` 数据内容，OpenAI 兼容端点也使用独立的 `user` 数据消息。稳定角色规则说明它是历史转述。运行时保留其独立类型和来源，聊天 UI、审计用户发言和角色送达统计不会将它计作真人发言。[现有协议适配](../../java/src/main/java/neuralcloud/controlplane/worker/ChatWorker.java#L502-L550)

## 四、摘要内容和来源契约

压缩调用使用同一 Chat Worker 模型。宿主对旧提要条目和带发言角色的新原文统一编号，从 1 起按输入顺序编号。回复只接受 `items` 和 `closed` 两个必填数组。`items` 的每项包含 `kind`（`TOPIC`、`CONSTRAINT` 或 `OPEN_POINT`）、非空自然语言 `text` 及非空的整数序号列表 `sources`。`closed` 的每项含上版未决条目序号 `previous` 和本批新证据序号 `evidence`，均为整数。无对应内容时提交空数组。宿主绑定会话、覆盖位置和来源版本。Gemini 复用结构化输出，OpenAI 兼容端点复用强制单一函数 `submit_chat_summary`。这个函数只提交候选数据。模型请求不提供检索、执行、发送或写 Memory 的能力。[已有结构化调用](../../java/src/main/java/neuralcloud/controlplane/worker/ChatWorker.java#L375-L399) · [Gemini 结构化输出](https://ai.google.dev/gemini-api/docs/structured-output) · [DeepSeek 聊天补全](https://api-docs.deepseek.com/api/create-chat-completion/)

- **提要写什么。** 保存话题、指代对象、用户明确提出且仍适用的约束、明确未完的请求。保留谁说的、否定、转述和更正后的状态。自然结束、群聊跳过、草稿和送达不明都不能推导出新的待办。用户说自己已完成某事，只能作为本人陈述。需引述原话、确认身份、落实承诺或判断新旧回执时，模型使用现有查证路径。压缩可以发生信息损失，语义保真由标注回放验收。
- **保留根据。** 宿主把上版条目的引用展开回原始事件，保留因果来源和适用的 Memory `recordId@revision`，检查结构、允许值、引用范围与最终渲染长度。每个上版 `OPEN_POINT` 必须在新 `OPEN_POINT.sources` 中出现，或在 `closed` 中出现一次，两者互斥。宿主可给有来源的本地回复附上已核验的业务回执类型和动作关联，用它核对动作是否可结项。单有聊天送达回执只证明说过这句话。用户明确取消要求，可据其新发言结项。依据不足时保留未决。若所有仍须保留的未决条目合计已超过提要额度，拒收本次候选并记录预算不足，覆盖位置保持原值。语义判断仍需抽检，正式工作项及执行状态由原业务组件维护。
- **哪些材料可用。** 先沿用 `dialogueBefore` 的同渠道、同会话、已送达及来源筛选，再关联可核对的回执和版本。QQ 群的发言者来自渠道事件。未知发言者只归为“群内一位成员”。跨会话 `source_refs`、临时授权材料、召回正文、工具原始输出、图片识别推断和模型草稿均不作摘要来源。引用过可变依据的本地回复，只有在依赖完整并能按原受众复核时才可进入。旧审计中缺少必要来源的记录跳过摘要，记录计数。每个 `sources` 列表去重，摘要的自引用、未来或异会话序号、未知字段、截断输出和无来源条目共用候选校验失败出口。
- **更正和撤权。** 压缩模型也是一次信息交付。带 Memory 依赖的原文和旧条目，在进入压缩模型、交给普通规划或答复模型前均按本轮受众核验引用权、版本、有效状态和期限。提交候选时复核依赖，最终渠道交付继续执行既有校验。`startTurn` 返回更正材料或出现 `memory_context_reset` 时，即使事件产生在本轮请求标记之后，也立即废弃受影响的旧提要和旧前缀，先送达本轮更正。来源已失效却仍在旧审计中的正文也不能作为降级输入。首版以整份会话提要失效换取清晰的恢复边界。[轮首刷新](../../java/src/main/java/neuralcloud/controlplane/memory/MemoryCall.java#L264-L298) · [Memory v2 依据复核](../../java/src/main/java/neuralcloud/controlplane/memory/ResidentV2.java#L1015-L1029)

## 五、保存、并发和失败恢复

摘要调用最后一条输入为 JSON 对象 `{"entries":[...]}`。每个条目由宿主提供从 1 起的整数 `index`、`kind` 和 `text`。旧条目的类别沿用 `TOPIC`、`CONSTRAINT`、`OPEN_POINT`，原文类别为 `USER` 或 `MISTY`。说话者、事件位置和已核实的业务回执由宿主另列，原文分片保留准确的片段正文。供后续轮使用的提要是历史转述，具体验证和动作仍走正式入口。

每次尝试写入 `chat_context_compaction` 审计事件。`status` 取 `COMMITTED`、`REJECTED` 或 `FAILED`，分别表示成功提交、候选未通过校验或操作失败。`revision`、`covered`、`offset` 反映实际生效的修订、覆盖事件和 UTF-16 偏移，`gapUnits` 是本轮未展开的原文长度。用量一律取供应商响应，缺少的计数保持缺省。

在该主体审计目录增加 `chat-context.sqlite`，沿用项目现有的 SQLite 依赖。每个 `Trace.Scope.sessionId()` 对应一份当前快照，另绑定 `conversationId()` 供授权复核。快照保存格式版本、修订号、最近重置点、已覆盖到的事件及可选分片偏移、条目与其原始依据。事件由 `(runId,eventId)` 标识，先后按审计文件的恢复顺序及文件内位置确定。`eventId` 在重启后会重新计数，不能单独作游标。[会话标识](../../java/src/main/java/neuralcloud/controlplane/console/ConsoleServer.java#L105-L137) · [原审计恢复顺序](../../java/src/main/java/neuralcloud/controlplane/console/AuditLog.java#L69-L89)

1. 每个会话同一时刻最多准备一个候选。快照固定为“本轮请求之前、最近重置之后”的连续合格事件。原文与已送达回复以各自可见的事件位置入列。摘要网络调用期间，其他会话及本会话新入站、送达回执可正常记账。
2. 提交时在同一 SQLite 事务中比对会话、基线修订和重置点，原子替换摘要、来源和覆盖游标。普通新入站保留在冻结点之后，自然成为尾部。并发落后的候选作废。本轮只能读取覆盖位置早于本轮请求的快照，防止较晚一轮已提交的内容倒灌。重置与提交按同一会话串行，使用前再核对审计重置点，避免审计与派生库之间的提交空档。
3. 摘要调用超时、格式非法、来源不符或持久化失败时，记录原因且不宣告成功。已确认未变的最后一份快照可继续使用，按硬上限保留最近连续完整原文。如果中间有合格消息因预算暂未进入输入，计入缺口并用短句向模型标出历史未展开。缺口标记也计入预算。来源失效时只取重置后或重新核验通过的材料。Memory 无法核验时执行既有查证失败语义。若提交结果不确定，下次先读已提交修订对账。后续请求从实际覆盖点续做。
4. 旧会话首次启用时，从已有审计和最近有效重置点开始惰性建立提要。重启只恢复已提交版本。覆盖来源缺失、格式不受支持或授权范围不匹配时，丢弃该派生快照并从可用原文重建。诊断记录修订、起讫位置、摘要长度、保留原文数、缺口、耗时、模型实际用量及失败原因。生产摘要正文存入与原审计相同访问范围的派生库，常规审计以指纹关联。隔离 Playground 开启完整模型输入采样时，沿用实验目录的访问权限。原始审计和 Memory 记录保留各自的追溯路径。

## 六、实施顺序和上线判据

1. **确定入口契约。** 在 `AuditLog` 分开“筛选带来源的事件”和“渲染最近原文”，共用现行渠道与送达规则。由 `ConsoleServer.Trace` 暴露当前请求截点和原受众。保留现有原文投影供 QQ 参与判断及未启用配置使用。先由独立子代理按本方案分功能编写、复核并提交一正一反的黑盒测试，再编写对应生产代码。
2. **接入压缩与恢复。** `ChatWorkerConfig` 定义启用方式和预算，`ChatWorker` 复用两个供应商适配器生成候选，控制面负责快照提交、来源复核和审计。`ConsoleMain.workerTurn` 及已有的无 Memory 规划入口在计划与回复之间传递同一快照。首版改动集中在 Harness。用现有 Memory v2 受众读取和版本复核接口，Master Epoch 和长期记忆写入继续由现有组件负责。
3. **在隔离回放中对照。** 固定模型、角色、采样配置和历史截点，在回环渠道对照 `OFF` 与 `ROLLING`。覆盖网页、QQ 私聊和可回复群，检查两个供应商的实际请求及正式送达出口。首次回放在目标截点以内重建，各实验侧只可继承本侧父运行在该截点前的有效快照。另补足能跨水位和连续多次压缩的合成长会话。记录各档位触发数、普通轮和触发轮各自的 P50/P95 延迟、硬上限处的缺口及原文保留量。核算整段对话的总输入、缓存命中和输出 token，把压缩调用本身计入额外成本。评阅者盲评远距离指代、未决事项、否定与更正、事实查证和角色表达。[回放与盲评入口](../harness/dialogue-playground.md)
4. **按结果启用。** 协议、受众隔离、撤权、旧候选拒收、重启及送达回归须全部通过，越权和伪造完成回执为零。建议在固定标注集上，长距离指代与待办延续正确数高于现有裁剪，短历史的同配置模型请求语义等价且额外压缩调用为零。对旧前缀可在本批处理、最近原文能放入目标额度的会话，核对成功整理后的历史长度。失败、积压及单条超长的轮次分别计数。首轮回放报告列出样本量、模型用量、触发轮 P95 增量和可接受的成本与延迟上限，锁定上限后在独立样本复验。人工评审通过后，先对隔离实例、再对选定服务实例启用 `ROLLING`。回退时恢复启用前的配置，设为 `OFF` 并移除显式的 `historyBudgetUnits`，按现有流程重启。恢复启用时重新验证快照和来源。[项目守则](../../AGENTS.md)

## 七、黑盒验收用例

以下为实现前确定的验收条件。从隔离网页或 QQ 回放发言，观察模型请求、渠道交付和审计诊断。除另述外，使用默认预算的 `ROLLING`，长度含可见标签。

1. **水位与截点。** 两例均让规划选择读取对话历史的普通 `REPLY`。正例将无积压的历史填至 36,000，旧前缀可在本批处理，最近原文能放入目标额度。发出新问题后仅见一次摘要调用，输入无新问题，规划与答复复用同一提要，整理后历史不超 24,000。反例将历史减至 35,999，用同一问题跨线，摘要调用为零，问题逐字保留。
2. **配置与参与。** 正例在越过水位的可回复群让 `AMBIENT` 判为参与，先用近期原文判定，再发摘要请求。反例分别用 `SKIP`、仅观察群、网页缺省配置回放，均无摘要请求。给 `OFF` 单配预算则在读取时报出 `historyBudgetUnits`。
3. **指代与草稿。** 正例让用户说“周五还是周六，等我定”，跨两次整理后问“我在选哪两天”，答复保留两日和未定状态。反例仅在未送达草稿中写“还欠一份清单”，摘要输入无此句，续聊也无补发待办。
4. **未决结项。** 正例给既有“提交报表”补入同一动作的成功业务回执，让摘要模型据此结项，下轮提要不再列为未决。反例只送达“我去提交”，让模型用这句话结项，候选校验失败，原未决仍在。
5. **受众与更正。** 正例将原受众可复核、依赖完整的本地回复置入甲会话旧前缀，摘要请求含其独有标记。反例在同渠道的乙会话预置另一标记，甲会话的摘要与同轮规划请求均无乙标记。对甲的旧来源分别在版本未变时撤权、在本轮请求标记后返回仅含新值的更正。后续模型请求与交付均无甲的旧标记，更正场景先交付更正。
6. **并发与重启。** 正例挂起甲轮摘要，从同会话发乙消息，甲轮模型请求无乙标记。提交后重启，下一轮近期原文含乙消息一次。反例在挂起时先重置，再交回旧候选，诊断显示拒收，重启后提要与原文均无旧标记。
7. **整条与分片。** 正例让唯一历史发言长 37,000，规划保留整条且无摘要调用。反例将超过单次压缩输入预算的旧消息置于近期原文之前，在拟切点放一个表情。分批中途重启，每轮最多一次摘要请求，各片首尾均为完整码点，拼接可还原原文。
8. **失败与缺口。** 各例均从同一份已提交、来源仍有效的提要开始，记下基线修订和覆盖位置。正例返回合法候选，审计修订和覆盖位置一起前移。反例令未覆盖历史超过 48,000，分别返回越界来源、模拟摘要超时。基线修订保持，规划含原提要、连续整条近期发言和缺口提示，历史段总长不超 48,000，下轮从基线覆盖点重试。
9. **协议与模型窗口。** 正例在两种供应商协议上回放同一轮，提要均单列为 `user` 数据，置于角色规则和近期原文之间。反例仅让本轮问题与固定材料超出窗口，沿对应模型契约报告错误，不能截短问题后作为成功答复。

## 八、实现与隔离验收

独立测试作者先按入口、出口和预期提交黑盒用例。宿主实现从同一条渠道审计链提取原文、送达和业务回执，按当前受众复核可变来源，将已验证的候选和覆盖位置一起写入 SQLite。供应商只接收编号后的资料并提交候选。原文、任务执行和 Memory 写入各自保留原有责任边界。[会话投影](../../java/src/main/java/neuralcloud/controlplane/console/RollingChatContext.java) · [来源与候选验证](../../java/src/main/java/neuralcloud/controlplane/console/ChatSummary.java) · [配置与复现命令](../../java/README.md)

JDK 21 离线 Maven 全量验证通过 98 项，含 38 个压缩专项测试及 4 个 Master Epoch 换代、回滚和重启隔离测试。Gemini 原生协议与 OpenAI 兼容协议均使用回环模型核对请求格式、完整输出、截断拒收，以及无 Memory 时的规划类别和查询字段。隔离渠道验收使用正式 Harness、Memory v2、HTTP 控制台及回环 OneBot，覆盖 QQ 私聊、可回复群、仅观察群、同版本撤权、轮首更正、发件前授权变化和丢失发送回执。另用支持身份目录的 Memory v2 核验按原用途送达、同一修订的目录撤权，以及目录称呼与普通历史的隔离。Playground 的两个快照隔离测试通过。

**真实模型回放。** 首轮实现使用同一 `deepseek-flash` 档位和 48000 单元预算，在本地网页会话入口执行同一组合成历史的三次成对重复。每侧各完成 9 个轮次，含短对话、跨水位和远距追问。统计含 Router、规划、答复和摘要的所有模型调用。供应商返回了每次调用的输入、缓存命中及输出 token。

- OFF 共 27 次调用，输入 392033，缓存命中 235264，输出 1065。9 个轮次 P50 为 2895 ms，P95 为 4894 ms。
- ROLLING 共 33 次调用，6 次摘要全部提交，短轮额外摘要调用为零。输入 306881，缓存命中 19072，输出 3175。3 个普通轮次 P50 为 3133 ms、P95 为 3457 ms。6 个触发轮次 P50 为 4936 ms、P95 为 12140 ms。相同阶段逐对比较，触发轮次增量 P50 为 1793 ms、P95 为 8768 ms。
- 两侧在 3 次远距追问中均答出了两个地点及等待条件。OFF 在前一轮已送达的回复中主动重述了这三条线索。ROLLING 将它们保存在提要，6 次成功提交均无原文缺口。总输入减少约 21.7%，供应商报告的未缓存输入由 156769 增至 287809，输出也增加。估算试点账单时应按这三类实际用量分别计价。
- 早期校准曾在 OFF 远距轮收到一次不符合现有规划契约的返回，该轮未交付。以上三对重复是随后完整运行的结果。回放工具保留失败、供应商实际结束原因和缺失的配对。

**独立固定截点。** 另建 142 条、50279 单元的合成历史，先登记两个备选地点和一项等待条件，再从完全相同的截点提问。期间没有可把答案带进近期原文的角色回复。首条线索、问题和评分项由测试作者在模型调用前登记。历史 SHA-256 为 `21f51d85aea564abe37b0a7b1d8b92062a5407eefd4a19a184e3eba55a4acdb6`。

- 首次真实模型运行中，OFF 三次均未答出，ROLLING 三次摘要均成功提交并保留线索，但只交付一次正确回复。另两次在无 Memory 的网页入口选择了枚举之外的 `HISTORY`，宿主拒收。
- 规划指引改为按本轮开放类别生成后，ROLLING 三次均交付了两个正确地名和等待条件。OFF 三次都选对了澄清，却在须留空的 `query` 中填入了澄清理由，宿主按原契约拒收。两次回放的失败轮均保留在各自的结果中。
- 最终版本在仅允许空查询的轮次，同时向两个协议声明 `query` 的唯一合法值为空串。用同一输入指纹再跑三对，六轮均正常交付。OFF 三次均询问用户补充线索。ROLLING 三次均答出「槐纹坞」「棠釉埠」和「等索道检修报告」，其中一次额外评论了用于填充历史的重复标本页。此处得分只衡量地名和等待条件，回复相关性须单独评审。
- 该截点是旧会话首次整理。三轮 ROLLING 共 12 次模型调用，输入 180626 token、缓存命中 6656、输出 1491。OFF 共 9 次调用，输入 109140、缓存命中 72448、输出 312。三对触发轮的时延增量 P50 为 2258 ms、P95 为 2854 ms。首次建立提要的全轮成本应与已有提要的续聊分别观察。

**最终版本的三阶段复跑。** 在上述修正后，以同一档位和预算重跑短对话、首次跨水位和远距追问，两侧共 18 轮全部交付。3 次远距追问中，ROLLING 全部命中两处地点及等待条件，OFF 命中 1 次。ROLLING 的 6 次摘要均成功提交，原文缺口为零，3 个短轮均未调用摘要。6 个触发轮逐对计算，耗时增量 P50 为 1148 ms，P95 为 2685 ms。

OFF 的 27 次模型调用合计输入 321015 token，缓存命中 212736，输出 1060。ROLLING 的 33 次调用合计输入 305695，缓存命中 18944，输出 3267。总输入减少约 4.8%，未缓存输入从 108279 增至 286751。每组只有三次重复，线上成本与延迟仍需按真实档位、流量和缓存命中核算。

Gemini 线上时延、实际 QQ 流量分布、人工盲评及业务可接受的延迟和成本上限仍待试点评审。默认配置为 `OFF`。
