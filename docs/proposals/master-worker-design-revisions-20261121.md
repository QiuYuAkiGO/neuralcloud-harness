# NeuralCloud Master 与 Worker 设计修订草稿

2026-11-21 起草，供共同评审。每个议题分别记录项目方提出的修订、供讨论的方案和仍待决定的问题。后续讨论可在对应议题下补充反例、替代方案或已采纳的决定。

## 修订一　跨会话更正与 Worker 记忆读取登记

### 项目方提出的设计

为每个 Worker 进程绑定一份记忆读取注册表。Worker 调用相关记忆时，把本次调用读取了哪些记录登记进去。某条记忆被更正后，系统可以按记录找到读过它的下游 Worker，及时通知对应进程。即使两个 Worker 分属不同会话，也能知道谁可能仍在使用旧信息。

目前开放的是通知到达之后的行为。正在组织回复的 Worker 需要保持会话连续性，准备按旧信息采取行动的 Worker 又有时效要求。项目方希望避免每次更正都打断正在进行的模型推理。原提案已提出按依赖刷新，本次修订进一步明确了登记时机和注册表与 Worker 进程的关系。[认知架构提案第 4 节](master-worker-cognitive-architecture-20261117.md)

### 编排器的归属

本稿采用 **Java 控制面内的独立编排模块**。首期编排器与 Router 可以部署在同一 JVM。Router 负责语义分流、整理上下文和拆解 Master 的意图，向编排器给出目标 Worker、任务及依赖。编排器负责实际派发、读取登记、更正通知和重启恢复。

读取注册表按 Worker 进程实例绑定，由编排器维护。记忆服务提交更正后，编排器消费 `/v1/changes`，查出受影响的 Worker，并将待通知事项与消费进度记入可恢复状态。即使 Router 此时没有执行模型调用，更正也能到达 Worker 的待处理区。重启后的补发由编排器负责，记忆正文和修订仍由记忆服务持有。

### 候选方案　及时通知进程，在使用旧信息前更新

建议由运行时登记实际交给 Worker 的记录标识（`record_id`）和读到的版本（`revision`），覆盖主动读取和自动注入。更正到达时，运行时立即把受影响的记录标为待复核，允许当前生成自然结束。这样可以分别处理“进程已收到通知”和“模型已使用更正后的依据”两个时点。

| Worker 所在时点 | 建议的处理方式 |
| --- | --- |
| 正在起草回复或处理内部步骤 | 暂存更正，无关步骤继续。多次更正同一记录时，保留变更历史，给模型的更新可合并为一次。 |
| 即将构造下一轮模型输入 | 按当前会话的可见范围重读待复核记录，在原会话末尾追加标明来源场合和可引用范围的记忆返回样板句，保留此前对话。来源已撤回时，说明哪项依据已失效。 |
| 本轮准备发送依赖该记录的回复、执行工具或提交派生摘要 | 向记忆服务核对所依赖记录的当前版本和有效状态，避免通知尚在路上时放行已过期的输出。发现冲突就暂缓这项输出，让 Worker 依据最新材料重做相关部分。派生摘要的来源版本需要在写入事务内核对。 |

例如，A 在项目群收到小林的改期消息，任务会话 B 正为该群起草周五 15 时的提醒。按这个候选方案，B 可以写完草稿。若下一步就是发送，编排器先暂缓旧提醒。B 下一轮收到记忆工具的返回“小林在项目群里说，会议时间已从周五 15 时改为周六 10 时。这条消息仅可在该群引用。”任务指令“请重新核对待发提醒”另行给出。若渠道已经确认送达，则保留原回执，另行处理对外更正。

注册表还需识别**依据失效但版本号未变**的情形。现有记忆服务在来源更正后，可将此前生成的摘要标为 `SOURCE_CHANGED`，摘要自身的版本号仍保持原值。初版评估也复现了另一种顺序，即旧摘要可能在更正后才提交。这两种情况分别检验通知消费和提交时复核。[初版可行性评估第 4 页](NeuralCloud重构可行性评估报告-初版-20261121.pdf#page=4) · [记忆存储实现](../../src/neuralcloud/storage.py)

### 留给下一轮的决定

1. **登记的有效期。** 一条记忆读过之后，怎样判断当前任务仍依赖它？Worker 进程退出或重启时，编排器应把哪些未完成任务的依赖重新绑定到新实例，又应在何时回收旧登记？
2. **读取与登记之间的空档。** 如果更正恰好发生在读到旧版之后、登记完成之前，怎样借助变更游标或版本复核补上这次通知？
3. **用户已经看见部分输出时的边界。** 普通草稿可以等到下一轮。流式回复若已展示旧时间，或工具请求正在等待渠道接单，应在什么时点暂停余下输出、核对回执并向用户更正？

Worker 的具体更新方式仍待讨论。可先用同一个会议案例分别比较“更正早于发送”和“更正晚于送达”，再决定哪些场景值得打断生成。

## 修订二　样板句在记忆工具返回中的作用

**项目方明确的定义。** 样板句是记忆工具的返回内容在送入或送出主模型（Master）或 Worker 时使用的自然语言包装，专用于承载这次工具返回的记忆。送入模型时，适配器用工具实际返回的数据填句。模型输出中需要继续传递这段记忆时，样板句保留其内容、来源和可见范围。模型据此形成的判断、派给 Worker 的任务和面向用户的回复各用自己的正文表达。

**可由 SQL 解释**指句式有确定的含义，每个可变部分都能对应到记忆数据。更正句可以写成“《说话人》《发言场合》说，《事项》已从《原值》改为《新值》。这条消息可在《可引用范围》引用。”执行层按契约把需要核对的值绑定为 SQL 参数，适配器从实际查询结果及其关联的来源和可见范围填句。这里列的是逻辑字段，具体表列和 SQL 模板由记忆适配器契约确定。

Java 实施稿第 1.2 节也用“样板”描述检索和写入请求。本草稿把发起操作的表达称为“检索请求”或“写入请求”，将“样板句”专指工具的记忆返回。按修订一的候选方案，注册表登记工具实际返回的记录标识和版本，即使两条记忆措辞相同，也能分别追踪其修订。[Java 实施方案第 1.2 至 1.4 节](master-worker-router-java-implementation-20261118.md)

### 精简召回时把可见范围写进正文

新版召回在裁剪时保留每条记录的来源会话和可见范围。执行层先按接收角色与会话校验可读范围，适配器再把“对方在哪里说的、这条记忆可以在哪里引用”写进交给 Master 或 Worker 的样板句。主动读取、自动召回和更正后重读均采用这个约定，精简内容时一并保留范围说明。

例如，小林在私聊和项目群说过同一句话，工具确认两条记录分别只允许在原会话引用。适配器在相应的授权上下文中返回以下样板句。

- **私聊记忆**　“小林私下和我说，会议改到周六 10 时。这条消息仅可在我与小林的私聊中引用。”
- **群聊记忆**　“小林在项目群里说，会议改到周六 10 时。这条消息仅可在项目群内引用。”

“私下”和群名取自已核实的来源会话，“可在哪里引用”取自实际授权。当前事件的 `privacy` 字段表示隐私等级，单凭其默认值无法判断发言场合。旧记录缺少场合信息时，样板句只写能够确认的来源和范围。验收时将同一正文分别作为私聊、群聊记录召回，直接检查模型收到的两条正文，并检查未获授权的另一会话收不到该条正文。[现有事件与渠道字段](../../src/neuralcloud/contracts.py#L84) · [现有插件召回裁剪](../../plugins/dsh-neuralcloud/src/index.mjs#L82)

## 修订三　由 Worker 自主判断是否提出异议

现阶段由承载 Worker 的大模型结合任务、上下文和 Master 的决定，自主判断是否提出、继续或结束异议。Worker 可以用自然语言解释自己的考虑，有相关依据时可以一并引用。例如，Worker 重读原有承诺后发现两项安排相互冲突，即使记忆库没有新增记录，也可以请 Master 重新考虑。Master 评估理由并决定下一步。

旧稿的“一次异议”上限和“须有新记录或新版本才能重提”在新版暂缓采用。编排器负责转交并记录裁决经过。Master 采纳异议后若要调整外部动作，编排器在派发时校验授权和依据版本，并跟踪实际回执。[原运行机制第 2 节](master-worker-runtime-discussion-20261117.md)

## 外部评审待议事项

2026-11-21，根据 Claude Opus 5.5 的 Canvas 评审与当前代码核对整理。以下是待讨论的问题及候选做法。Java 首期范围仍由项目守则指向的实施方案界定，即在同一会话走通会议改期。示例中，更正先入库，Master 随后取证并提出核对提醒。样板句如何表达记忆、SQL 在哪里执行、谁拥有写事务，分别需要对应的契约。[项目守则](../../AGENTS.md) · [首期流程](master-worker-router-java-implementation-20261118.md) · [事务归属待定项](master-worker-router-software-design-20261119.md)

### 接口与恢复仍需细化的问题

1. **更正游标的提交时点。** 插件的会话日志暂存游标与记忆变更流的消费游标各自记录不同的进度。编排器拥有后者。可用“已收到更正、尚未通知 B 就崩溃”验证待通知事项和游标能否一同恢复。具体持久化方式待定。[插件会话游标](../../plugins/dsh-neuralcloud/src/index.mjs#L166) · [记忆变更流](../../src/neuralcloud/storage.py#L346)
2. **多来源的披露范围。** 单条召回结果按修订二传达可见范围。从多条私聊观察派生的摘要或 Master 指令可能同时涉及不同参与者，向另一 Worker 转交时，允许披露给谁仍需明确。
3. **为样板句保留可验证的原始证据。** 现有 `SourceEvent` 对类型和附加字段有明确限制。应逐类核对用户陈述、工具尝试、送达回执、暂定印象如何持久表达，再决定哪些字段需要扩展。Router 做语义分流或去噪时，可将改写另存为带来源及读取版本的派生内容。原始消息和实际回执仍可追溯，权限过滤、去重、预算及依赖登记由执行代码落实。[事件契约](../../src/neuralcloud/contracts.py#L84) · [带来源的派生写入](../../src/neuralcloud/api.py#L154)
4. **更正与撤回的操作权限。** 当前服务使用共享令牌，`expected_revision` 校验写入依据的版本。接入多个角色时，需界定谁有权改动哪类记录。Worker 表达异议按修订三处理。[服务鉴权](../../src/neuralcloud/api.py#L41) · [更正处理](../../src/neuralcloud/storage.py#L233)

### 在相应功能引入前验证

- **推理资源与抢占。** 在约 9B 的目标部署上测量顺次处理与 Fork 的实际等待时间和资源占用，再决定是否启用 Fork。普通记忆更正按修订一讨论的自然边界处理。
- **第 3 类冲突与聊天等待。** 用事实改期、局部实现选择和两项互斥承诺等案例观察模型判断，再决定聊天可以等多久、逾时回复什么，以及由谁跟进。评测样例供复盘模型表现使用。
- **换代与长期状态。** 可把未决承诺、裁决和期限保存在编排器的持久记录中，让新上下文据此重建。标签摘要的取舍仍可由模型完成。还需逐项确定旧归档的保留与清理、印象写入预算及其与事实召回的配额、MistyAI 状态服务采纳建议的字段与限幅，以及云端切换时允许传递的数据、适配器兼容性和冷缓存延迟。
- **防止多个模型按不同版本实施。** 对决策、等待、Fork 和换代等跨轮机制，可在各自的权威规格集中记录触发条件、持久化时点和失败后的恢复行为，由其他文档引用。Canvas 的评分、机制数量和“90% / 10%”工作量设想可作讨论背景，验收应使用本项目的用例和测量值。
