## 2. 主体分工、路线 B 与冲突分流

### 2.1 路线 B：Master 定位为“反思记录核心 + 极低频终审”

**已确认决定（2026-11-20）**：采纳 **路线 B**——Master 常态以**主体反思与记录核心**运行（约 90% 工作负载，负责观察消化、写带个人色彩的主观印象/心声、提交内稳态建议、维护只读偏好与关注焦点摘要、复盘与日记），仅在极低频的第 3 类冲突中行使**内部最终裁决权**（约 10%）。

### 2.2 三类冲突分流边界

并非所有冲突都发给 Master；必须将工程冲突与主体价值冲突彻底隔开：

| 冲突类型 | 典型例子 | 处理归属 | 是否发给 Master 同步裁决 |
| --- | --- | --- | --- |
| **第 1 类：事实 / 版本 / 资源冲突** | 计划版本更正（`revision 2 → 3`）、记忆返回 `CONFLICT`、多 Worker 争抢同一文件 | **Orchestrator** 凭 `record_revision` 与依赖检查拦截重规划；事实矛盾由 **Worker** 查证或向用户核实 | **否**（Master 仅事后异步记录） |
| **第 2 类：任务内局部技术 / 策略冲突** | 编码实现选型、工具失败重试路径、局部步骤拆解 | **Worker 自主决策**；越权或不可逆外部动作走确定性审批找用户 | **否** |
| **第 3 类：主体偏好 / 价值 / 意图冲突** | 重大主体偏好取舍、重要承诺、明显方向背离、跨会话意图相悖 | **Master 内部终审**（可主动介入、纠偏或终止 Worker） | **是**（极低频高优通道） |

### 2.3 Worker 自主权与 Master 最终控制权

Worker 可以在局部任务中自主判断、规划和执行，并主动上报关键节点；Master 亦可通过观察流自行发现偏离并主动介入。

在内部意图与决策链上，Master 对 Worker 拥有最终控制权（含查看记录、调整方向、正常结束与紧急终止）。Worker 在**同一条冲突中只有一次异议机会**；Master 听取异议后仍坚持原决定时，Worker 无条件服从，即使该决定实际上可能错误。

**外部边界不变**：内部控制权不表示 Master 天然正确，也不允许 Master 绕过既有外部工具授权、敏感动作审批、隐私边界及事实核验规则。Master 不直接与用户沟通，只与 Worker 沟通，由 Worker 向用户说明、讨论和反馈。

### 2.4 新事实重提的确定性判定协议与责任

**已确认决定（2026-11-20）**：采纳基于版本证据集合的确定性协议，防止自然语言重复争辩伪装成“新事实”：

- 每次第 3 类冲突分配唯一 `decision_id`，并记录其依赖的 `evidence_set`（`record_id + revision` 集合）。
- 仅当长期记忆或已提交观察中出现了**不在原 `evidence_set` 内的新 `committed observation` 或更新后的 `revision`** 时，协议层才放行“新事实重提”并允许暂停相关行动。
- 否则视为同一冲突，协议层强制执行 `max_objections = 1` 上限。

Master 需对自己的决定负责，进行复盘并安排必要补救。复盘记录格式与补救完成标准随编码阶段细化。

## 3. 准实时观察与评价

### 3.1 主要观察方式（放弃原始 CoT）

**已确认决定（2026-11-20）**：**正式放弃读取 Worker 原始思维链（CoT）**（商业 API 能力不可靠、噪音与污染成本过高，且避免过度依赖 Master 能力）。Master 对 Worker 的常规观察输入统一改为四类结构化内容：

1. **结构化进展**（Worker 当前状态、重要进展与主动上报的关键节点）；
2. **拟执行动作草案**（正在考虑的选项及准备采取的关键动作）；
3. **关键工具结果**（已执行动作的结果与持久回执）；
4. **思考摘要**（若底层模型或协议提供精简思考摘要，仅作参考，不冒充原始 CoT）。

必要时 Master 可按需回看相关对话与完整上下文记录。此决定亦彻底消除了早期草案与总体提案第 9 节“不跨会话传输原始推理链”之间的口径冲突。

### 3.2 关注节奏

一般情况下，Master 关注重要进展；在对话和编码等关键阶段进一步挖掘、思考。准实时不等于每一步都需要批准，也不预设固定轮询周期或强制持续生成。

Master 的评价和记录带有所用语言模型与提示词形成的个人色彩。观察事实与主观解释严格区分，不能把评价当成外部事实。

### 3.3 防止过度思考

深入思考不应违背设计原则，也不应解读出不存在的含义。需要区分：

- 当前证据未完全明说，但结合记忆有依据的潜在含义；
- 缺乏依据、由模型自行添加的含义。

Master 应结合记忆进行综合判断（并保留经由记忆网关主动查证的能力）。不确定性表示与过度思考评测阈值留待实验阶段校准。

## 4. Worker 分类与偏好信息

### 4.1 General-purpose Worker

General-purpose Worker 尽量不注入主体偏好信息，也不默认注入情绪类的内稳态转写，以减少上下文污染。只有在 Master 尝试说服 Worker 的情况下，才会按需提供相关偏好信息；内稳态侧最多在必要时提供硬性资源/节流约束。

### 4.2 Chat Worker

Chat Worker 持有一份**精简、持续更新的偏好摘要**，并接收 Router 按角色投影的**精简内稳态基调/精力约束提示**：

- 偏好摘要由 Master 维护，Chat Worker 只读不可修改；
- 可据此完成轻微的偏好选择；
- 值得认真考虑的第 3 类事项仍提交 Master 终审。

轻微与值得认真考虑的具体分界、偏好摘要字段与更新频率随编码细化。

## 5. 硬性介入与行动冻结

Worker 提交事项时，需要明确说明是否请求硬性介入（`hard_wait`）：

- **硬性介入**：Worker 等待 Master 作出决定，但只冻结受影响的关联行动；不依赖该决定的工作可以继续。
- **非硬性事项**：进入备忘录，由 Master 按优先级与调度规则处理。

**已对齐优先级语义**：`hard_wait=true` 只对 Worker 自身的等待义务生效，是 Router 裁定优先级时的输入特征，**不自动等同于 P1**。例如后台编码任务的非紧迫硬等待可排入 **P2**（冻结相关步骤，待主干顺次处理，不滥用 Fork）；只有强实时或关键时效的第 3 类冲突才定为 **P1**。

- **未确认建议（Chat 场景兜底）**：Chat Worker 单轮回复较难拆分子步骤局部冻结；尽管同前缀 Fork 已大幅降低等待延迟，但遇同作用域排队或云端 API 抖动时，建议仍为 Chat Worker 预留短同步等待超时，超时后降级为自然缓冲回复并转异步跟进（具体超时策略与秒数待编码前确认）。

## 6. 备忘录、期限与日记

### 6.1 两类具体事项

备忘录可以同时包含：

- **待决策事项**：有具体问题或选择需要 Master 判断。
- **待执行事项**：有具体、实际可行的要求需要落实。

二者必须明确区分。不能把“成为一个更好的人”这样没有实际落点的抽象想法直接列入备忘录；这类内容属于日记。

### 6.2 决策先于执行

关联的待决策和待执行事项允许同时存在，但必须按**决策 → 执行**顺序处理：完成决策后，才能考虑关联执行。

决策完成后，如果没有直接对应的执行，Master 可以自行决定是否将其转写为执行事项，以及是否设置执行期限。不要求每项决策都产生行动。

### 6.3 deadline 与处理时机

Master 可以为非硬性事项设置 deadline。平时可以等各 Worker 没有新事项或新刺激时再处理，但到期必须主动提醒 Master，不能一直等待空闲。

到期事项参与优先级竞争。“允许竞争式调用”需要结合后续“只能有一个 Master”理解，不能据此前早期表述实现多个并行的正式决策 Master。

期限字段是否分别表示最晚决策时间与最晚执行时间、逾期如何处理，尚未确定。已确认的是到期提醒和关联事项的先决顺序。

### 6.4 日记

日记由 Master 主动写，是否写、写什么及是否进一步转化为行动，都由 Master 判断。

日记作为参考，不设定产出要求，不要求每篇日记生成任务，也不把抽象愿望自动变成待执行事项。

## 7. 唯一 Master、Router 模型池与四档优先级

### 7.1 唯一性要求（逻辑单一主体）

**已确认决定（2026-11-20 对齐）**：坚持**逻辑上只能有一个持久主体与唯一活动主干 `Master-Main`**，不设立多个长期并行决策 Master。为兼顾低频紧急插队与上下文清理，允许两类严格受限的瞬时辅助实例：

- **同前缀临时 `Master-Fork`**（见第 8 节）：受作用域互斥、写权限白名单、创建期退出门禁与无中断回注约束，仅做单点紧急裁决，确认完结后立即销毁；
- **换代期只读候选 `Candidate`**（见第 10 节）：仅做基于标签的上下文瘦身与新主干准备，无决策权、无写权，直至原子切换 Epoch 租约。

### 7.2 离散四档优先级与三层裁定机制

**已确认决定（2026-11-20）**：放弃连续分数，采用**四档离散优先级（P0/P1/P2/P3）**，由**确定性硬规则托底 P0 + Router 结合只读关注焦点初定 P1/P2/P3 + Master 事后校准**共同裁定：

| 等级 | 语义边界 | 裁定主体 | 运行时行为 |
| --- | --- | --- | --- |
| **P0（紧急止损）** | 用户急停、不可逆危险动作拦截、系统安全边界 | **确定性硬规则**（0 延迟，不经 LLM） | 立即生效（阻断 Worker / 作废同域旧生成 / 紧急处置） |
| **P1（高优终审）** | 触及主体重大偏好/承诺且时效敏感的第 3 类冲突、到期关键 deadline | **硬规则初筛 + Router 语义确认** | 主干空闲直接处理；主干正忙非冲突或低优同域任务 → **允许触发 `Master-Fork`** |
| **P2（中优常规）** | 重要任务进展、非紧迫的硬性等待、常规待决策/待执行备忘录 | **Router 首轮定级**（Master 可重排） | 进入主干队列顺次处理；**不触发 Fork，不打断主干** |
| **P3（低优背景）** | 例行归档、非紧急复盘、写日记、长期整理与 dreaming 候选 | **默认归类 + Router 分流** | 主干空闲时消化；配合 **deadline 到期提权**与 **Aging 防饥饿** |

Router 仅在**事件首次入队时定一次级**，不反复重排队列；后续仅允许 **Master 主动调序**、**deadline 到期**与 **Aging 规则**改变顺序。

### 7.3 Router 模型池：无状态设计与四类逻辑职责

**已确认决定（2026-11-20）**：Router 设计为**池化的轻量模型池（计算资源复用）+ 单次任务级无状态（用完即销毁）**。需要短时历史的信息（例如最近数轮摘要、当前已注入的 `record_id` 集合、近期事件防抖计数）由 Orchestrator 外部确定性维护并作为参数传入，防止跨话题串味或演化出第二人格。

运行时共享同一模型池，逻辑上拆分为清晰子职责：

1. **入口分流与首轮定级（`DispatchRouter`）**：读取 Master 维护的极简只读**主体关注焦点摘要（Active Focus）**，完成 P1/P2/P3 首轮入队定级及创建新 Worker；后续 Master 可调整排序或关闭 Worker。
2. **记忆调用统一上收（`MemoryGatekeeper`）**：
   - **自动预召回（Push）前置门控**：在调用 NeuralCloud `/v1/recall` 前先判定 `SKIP / RECALL`（解决纯问好/寒暄盲目召回所有历史问好的问题）；需检索时做结构化 query 改写、已注入去重、隐私域过滤与字节预算裁剪。
   - **按需主动查证（Pull）代理**：保留 Master（及受控 Worker）主动发起 `memory_recall` / `memory_read` 的能力，避免信息垄断；主动调用统一走同一网关校验隐私、预算并登记 `relevant_record_revisions`。
3. **内稳态读向投影（`HomeostasisProjector`）**：
   - **确认需要读向投影**，按消费角色分级输出只读视图：给 Master 提供高保真低修辞的**客观内感读数**（保留 Master 自主赋予主观色彩）；给 Chat Worker 提供精简基调/精力约束提示；对 General-purpose Worker 默认不注入情绪转写。
4. **写入侧边界（不替代 Master）**：
   - Router 最多承担**外部观察通道的去噪与结构化**（严格忠于原文证据、保留 `evidence_ref`，不带主观推断）以及**客观运行负荷/资源特征提取**；
   - **严禁**替 Master 写入主观印象通道（`impression`）或做意义依赖型的内稳态情绪评估，避免架空 Master 或造成表里分裂。

## 8. 同前缀临时 Fork、作用域互斥与 Worker 终止

### 8.1 以同前缀临时 Fork 替代常规中途硬中断

**已确认决定（2026-11-20，替代早期 8.1 节“高优到来一律取消原 Master 生成”的方案）**：当 `Master-Main` 正在执行非冲突或低优任务，而高优 **P0/P1** 事件到来时，优先派生一个与主干前缀缓存一致的短命 `Master-Fork` 独立裁决，受以下 **4 条硬约束**保护：

1. **严格写权限限定 + 创建期退出门禁（Exit Gate）**：`Master-Fork` 仅可输出针对目标 `decision_id` 的裁决与依据，禁止修改偏好摘要、优先级表、日记或直接提交长期印象/主观内稳态建议。在创建时即固化退出门禁（结构化输出校验通过 + 裁决写入目标 Worker 下发通道 + 回注记录落盘进入主干队列，或触发硬超时/显式失败回滚），**确认全部退出门禁完结后才释放锁并销毁**。
2. **作用域互斥与同域排队**：
   - 当 `Master-Main` 忙于其他作用域时，直接锁定目标 `scope_key` 派生 1 个 Fork；
   - 当 `Master-Main` 正在同一 `scope_key` 上执行**低优在途生成**且涌入紧急事件 `E1` 时，允许将主干该笔输出标为 `SUPERSEDED`（不强杀 HTTP 流，返回时丢弃不下发给 Worker），立即派生 1 个 Fork 优先处理最高优的 `E1`；
   - **同一作用域严禁并发多个 Fork**：若 `E1` 尚在裁决中而同域继续涌入 `E2`、`E3`，后续问题进入该作用域等待队列，待 `E1` 通过退出门禁释放锁后，连同 `E1` 的已生效结果打包合并顺次处理；作用域锁配硬超时 TTL 回收，杜绝锁死。
3. **无中断强制回注主干（Merge-Back Barrier）**：`Master-Fork` 完结后将 `fork_decision_committed` 写入主干输入缓冲队列队头，**不中断主干当前生成**；待主干当前轮自然结束后，下一轮推理以 Append-only 方式搭便车注入，保持前缀缓存完整，由主干统一补记印象、复盘与状态建议。
4. **纯 Append-only 复用前缀**：Fork 严格复刻主干上一次已稳定落盘的精确消息前缀（前文零修改），仅在末尾追加本次紧急裁决输入，最大化命中本地或云端 Prefix Cache。

### 8.2 临时工作检查点（触发面收窄）

采用同前缀 Fork 后，常规 P1 插队不再中断主干生成，临时工作检查点仅在**极少数 P0 硬止损不得不中止在途长工作**时才会触发。

**待澄清语义（缩小后保留）**：在极少数 P0 中止场景下，临时工作检查点按“一轮逻辑工作完成或放弃后销毁”还是“更短生命周期销毁”，以及检查点最小字段集合，在编码实现 P0 中止分支时顺带对齐。

### 8.3 Worker 的两种关闭

允许 Master 选择：

- 正常结束 Worker；
- 紧急终止或强行关闭 Worker。

已经发生的动作和信息如实记录，不因终止而抹除。具体取消在途外部工具、等待回执超时与失败上报细节在 Java 控制面编码时定义接口。

## 9. Master 上下文、本地/云端回迁与 dreaming 边界

### 9.1 参数化水位与 1M 云端 API 预留

## 10. 基于标签的上下文清理与 Epoch 租约换代

### 10.1 已确认的换代与瘦身闭环（2026-11-20 采纳 Epoch 租约）

换代的核心宗旨是**清理上下文中已完结或不重要的内容**；引入 **Epoch 写租约**作为安全交接外壳，确保瘦身的同时“准备期不双脑、切换期不丢增量”：

1. **打标冻结**：上下文触及当前模型档位的换代阈值时，在 `seq = S` 处冻结各段上下文的简短标签清单（如 `xx-worker 执行记录`、`chat 待处理印象更新`）。
2. **只读候选瘦身**：启动**只读换代准备者（`Candidate-Epoch-(N+1)`，严格禁止向 Worker 下发决定、改队列、改偏好或提交状态变更）**，依据标签筛选出保留清单，剔除不重要的历史段落，组装出干净紧凑的新上下文并标记为 `ready`。
3. **安全边界补增量 + 原子切租约**：等原主干 `Epoch-N` **当前单步安全落盘**后，Orchestrator 短暂缓冲新事件，将准备期间原主干新产生的极少量增量段（`seq = S+1..current`）直接追加至新上下文尾部，**原子切换主干写租约至 `Epoch-(N+1)`**。
4. **归档与清除**：原 `Epoch-N` 立即失去写权并归档；待后续 dreaming 整理完跨任务关联后，清除不再使用的旧 Epoch 归档记录。

### 10.2 原第 10 节五个问题的定案状态

- **问题一（唯一 Master 与候选权限）**：**已解决**——准备期候选者严格只读无副作用，任何时刻仅有一个持有写租约的活动主干 `Master-Main`。
- **问题三（准备期新增信息交接）**：**已解决**——切租约前在安全静止边界停派发并将增量段追加至新主干尾部。
- **问题五（原 Master 交棒时机）**：**已解决**——以当前单步调用落盘为交棒边界，未完成逻辑事项随新上下文与队列平滑接手，避免长任务拖爆窗口。
- **问题二（极少数 P0 中止检查点销毁）**：随 Fork 机制已大幅弱化，仅保留在 P0 强制中止分支实现时确认。
- **问题四（标签具体格式与按需展开规则）**：进入编码阶段设计标签 DTO 时敲定（建议包含段 ID、简短内容说明、未决承诺/未决事项标记，并允许只读候选对拿不准的段落按需展开原文）。

## 11. 进入编码阶段的剩余待细化项

以下细节可在编写 Java 控制面代码与协议 DTO 时按模块逐项落地，不阻塞启动编码：

1. **Java 控制面模块边界与工程骨架**：Orchestrator、RouterModelPool（含 `DispatchRouter` / `MemoryGatekeeper` / `HomeostasisProjector`）、MasterMain / ForkRunner / EpochHandover、NeuralCloud HTTP Client 与共享状态接口划分。

## 12. 编码启动顺序建议

结合现有已可复用的 Python 版 NeuralCloud（`/v1/*` HTTP 契约）与 P0 合成样本方向，建议按以下顺序推进实现：

1. **确定性内核与契约先行**：在 Java 侧先实现核心不可变 DTO（`PriorityItem`、`DecisionConflictRecord`、`ForkContract`、`RecallGateDecision`、`EpochLease`）与 P0 硬规则、作用域互斥锁、退出门禁和 `evidence_set` 校验，并用合成事件跑通单元测试。
2. **接入 Router 无状态门控与 NeuralCloud**：打通 `MemoryGatekeeper`（先验证“纯问好 `SKIP` 零召回 + 主动查证代理”）与按角色分级的 `HomeostasisProjector` 读向投影。
3. **打通单主干 + 同前缀 Fork + Epoch 租约换代闭环**：用本地模型（及可切换的云端 API 适配器）在双 Worker 合成场景下验证无中断回注、同域排队、标签瘦身切主与本地不可用回迁。
