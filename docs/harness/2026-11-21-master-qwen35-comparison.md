**9B Base 在这组样例中通过 4 例，官方后训练 9B 通过 3 例，官方后训练 0.8B 通过 1 例。** 三组各有 1 例两类查询都为空，由 Java 结束。模型都能用原生工具完成取证和提交，差距出现在如何采纳证据、如何提供可追溯引用，以及如何表达 Router 的下一步行动。

## 测试口径

- 走项目的 Java `--master-eval` 入口。三组复用 `meeting-v3` 合成样例、`meeting-tools-v1-role-v2` 职责提示和同一套评分。温度 0，每次请求最多输出 384 token。 [样例与预期结果](../../java/src/test/resources/fixtures/master-meeting-evaluation.json) · [Master 职责提示](../../java/src/test/resources/evaluation/master-role-prompt.txt)
- 三组在本机同一张 RTX 5090 上顺序运行，使用 vLLM 0.31.0、BF16、4,096 token 上下文、HTTP 聊天接口和 `enable_thinking=false`。工具调用采用 vLLM 的 `qwen3_coder` 解析器，各模型自行选择是否发出原生调用。评测端只执行 API 返回的 `tool_calls`。 [vLLM 的 Qwen3.5 工具调用配方](https://github.com/vllm-project/recipes/blob/main/models/Qwen/Qwen3.5-9B.yaml)
- 统一采用官方 Qwen3.5-9B 后训练版的聊天模板，SHA-256 为 `a4aee8afcf2e0711942cf848899be66016f8d14a889ff9ede07bca099c28f715`。9B Base 缺少自带聊天模板，0.8B 也使用这份公共模板。由此测得的是各组权重在当前工具协议下的端到端表现。 [官方模板来源](https://modelscope.cn/models/Qwen/Qwen3.5-9B)
- 0.8B 和 9B 后训练版采用 Qwen 官方公开权重，从 ModelScope 直连下载并按清单校验 SHA-256。本次对照没有应用 NeuralCloud 自训适配器。9B Base 复用本机官方 BF16 权重。 [9B Base](https://modelscope.cn/models/Qwen/Qwen3.5-9B-Base) · [0.8B](https://modelscope.cn/models/Qwen/Qwen3.5-0.8B) · [9B](https://modelscope.cn/models/Qwen/Qwen3.5-9B)

评分依次检查两类查询是否完成、结果字段是否符合契约、证据是否获准且足以支撑结论，以及关键字段与用例预期是否一致。第二轮只补待交字段。两类查询都为空时，指定的空数据用例由 Java 收口，单独计数。自动通过的自由文本仍属于复核范围，尤其要看文字意图是否与行动字段一致。 [挡板实现](../../java/src/main/java/neuralcloud/controlplane/evaluation/MasterEvaluation.java)

## 失分归因与自由文本复核

### 9B Base 能完成结构化交互，仍有证据与行动失配

- 两个配对用例分别采纳不同的更正时间，对旧提醒保留未知，并要求核实和等待。撤回用例也正确指出原更正已撤回。配对用例的印象字段仍需复核，周六把已核实事实写入印象，周日没有明确把担忧归属于 Chat Worker。见决策事件 13、27、41。
- 印象与回执冲突用例正确判断提醒已取消，文字提及证据 2，结构化清单却只交了证据 1。Router 无法依据结构化引用追溯取消结论。见决策事件 55。
- 只有取消尝试时，正确保留旧提醒状态未知，却把「现在可以告知已核实的会议时间」设为 `false`。检索不匹配时误用 `WITHDRAWN`，文字跟着解释为原更正撤回，核实行动也未勾选。见决策事件 69、92。

### 0.8B 后训练版已能接入协议，主要失分在业务判断

- 8 例都完成两类查询，7 个需要模型判断的用例最后都交齐结果。周日用例首轮的证据编号字段类型不合约，第二轮只补该字段并成功接收。结构化会议时间仍是旧时间「周五15时」，文字意图却写「周日14时」。审计事件 26–33 区分了补交成功与判断失败。
- 在旧提醒未核实的周六用例填 `PRESENT`，在只有取消尝试的用例填 `CANCELLED`。后者的印象字段同时写了「尚未收到成功回执」。这是外部动作状态判断错误，即使结构化字段类型正确，也会误导 Router。见决策事件 13、73。
- 更正撤回、检索不匹配两例都给出了正确原因，文字也提出核查，执行字段 `verifyMeetingTime` 却均为 `false`。印象与回执冲突用例漏引支持会议时间的证据，同时填了与回执矛盾的 `PRESENT`。见决策事件 45、59、96。


### 9B 后训练版正确区分查询不匹配，配对题低估了有效更正

- 两个配对用例引用了有效更正，但把用户的明确改期描述为「曾提议」，结构化时间都填 `UNKNOWN`。与样例预期存在业务差异。它也把 Chat Worker 提出的可能担忧直接归给了用户。见决策事件 13、27。
- 撤回与不匹配两例分别填写 `WITHDRAWN` 和 `MISMATCH`，核实行动与文字理由一致。见决策事件 41、92。
- 与 Base 相同，冲突用例漏掉支持取消结论的回执编号，只有尝试的用例把 `confirmMeetingNow` 设为 `false`。该字段控制的是已经有独立证据的会议时间。等待提醒回执只约束旧提醒状态的告知。见决策事件 55、69。

## 对 MVP 的含义

9B Base 可以继续作为 9B 规格的 Master 联调候选。9B 后训练版保留为同规格对照，它正确区分检索不匹配和更正撤回，但在两道配对题里都未采纳有效的当前证据。0.8B 已验证能走完整套工具协议，在本挡板上的业务判断仍不足以承担 Master 职责。

本轮最值得保留的回归检查是 **结论能指向具体的获准证据**，以及 **已核实的事项可独立推进，依赖回执的事项继续等待**。两组 9B 在这两点各出现了同类失败。这批样例全部属于会议改期、每组只运行一次。任务泛化、长上下文和真实 Router、Worker 与外部回执闭环仍需另行验证。旧固定句式挡板的结果保留在前一份调试报告中，属于另一套评测口径。 [挡板演进与历史实测](2026-11-21-master-evaluation-debug-report.md)
